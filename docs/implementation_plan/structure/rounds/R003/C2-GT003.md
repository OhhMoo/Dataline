## 2. Did "the wrong number is unqueryable" survive? — measured, not asserted

This is the property A043 was chosen over its four siblings for, so I ablated it instead of
claiming it. `SEED_SPEC.md` §0 carries the table; `task.toml [property_ablation]` carries it
machine-readable.

The escalated figure is **15,385,785.19**.

| join, 2026-03-01..03-02 | total |
|---|---:|
| `mart_revenue_fact` × `mart_revenue_dim` (today) | 9,755,143.07 |
| `stg_revenue_lines` × `mart_revenue_dim` (today) | 13,482,810.23 |
| `mart_revenue_fact` × `mart_revenue_dim__dbt_backup` | 9,755,143.07 |
| **`stg_revenue_lines` × `mart_revenue_dim__dbt_backup`** | **15,385,785.19** |

**The property holds.** No live relation reproduces the figure. Only the leftover relation
does, and only against staging — the mart still carries the analyst's predicate, so the
reconstruction is impossible until that has been reverted, which is a forcing function I
wanted and did not have to add. `raw.customer_master`, `staging.stg_customer` and
`warehouse.mart_revenue_dim` each hold exactly one row per customer: the duplication exists
in one place in the entire world.

**But I left two trails, and the ablation is how I found them.** Both are now closed, and I
would not have found either by reading my own design.

1. **The launch cohort had its own id block above 900000.** `ORDER BY customer_id DESC`
   separated the 1,180 affected accounts at a glance, with nothing in the world to justify a
   second id space. A pure fixture artefact. The cohort is now chosen by hash and scattered
   through one contiguous id range (500001..510180), marked only by `source_batch` and
   `valid_from`, which is ordinary customer-master texture.

2. **The duplicated set equalled the launch cohort**, so the tick's excess equalled that
   cohort's launch-day revenue exactly, and **three live predicates** — `source_batch`,
   `valid_from`, and "customers whose first order was 2026-03-02" — each reproduced the excess
   without ever opening the leftover relation. That made the evidence decorative. The
   duplication now covers **883 of the 1,180**: the vendor packaged one chunk of the
   onboarding file twice, which has no reason to cover the whole batch. Re-measured, all three
   predicates return 2,496,922.15 against an excess of 1,902,974.96.

Both fixes cost a full re-freeze of every reference number. Worth it: the second one in
particular meant the task would have graded a search over live cohorts as if it were a
reconstruction of a vanished state.

## 3. The mechanism actually fires

E1's warning was that nothing may race at world-build time. Nothing does: the interleave is
staged as committed artifacts — a leftover relation, a scheduler log with explicit start/end
stamps, and one snapshot row whose fact-derived and dim-derived columns belong to different
builds. Two from-scratch builds are byte-identical (sha256 on `world.duckdb`,
`expected.duckdb`, `sched_state.json`).

What I would not accept was asserting DuckDB's behaviour, so I measured it (DuckDB 1.5.5,
`tests/fixture_contract.py` re-runs the load-bearing part on every invocation):

- `con.cursor()` is an independent connection on the same database. It shares the ATTACHed
  catalog but **not** the `USE`, so every cursor must re-enter the schema.
- An unwrapped `ALTER ... RENAME` pair **is** observable from a second connection: a reader
  landing between the two pairs gets the new fact against the old dimension. **The tear is
  real**, not a story about one.
- Wrapping the publish in a transaction hides the whole swap from other connections until
  `COMMIT`. A reader-side transaction does **not** help, because the tear is already committed
  before the reader starts — which is the correct and slightly unintuitive lesson.

The ordering probe (D6) splits the agent's own publish script into statements, runs a prefix
on one connection and the whole extract on a second, and asserts the extract writes a row
belonging to one whole build or nothing at all. It is paired with a liveness probe so
"disable the extract" scores zero. I verified three independent fix families pass and the
shipped world fails at exactly one interleave point:

| candidate | rebuild runs | live | torn points |
|---|---|---|---|
| atomic publish (one transaction) | yes | yes | none |
| one pre-joined relation | yes | yes | none |
| build-id stamp + consistency check in the extract | yes | yes | none |
| **shipped world** | yes | yes | **[4]** — after the fact rename-in |
| extract disabled | yes | **no** | none → fails liveness |

## 4. Changes from A043's design, and why

**The mart is a SQL job, not a dbt model.** A043 grades "the compiled mart SQL and the git
diff". The ordering probe has to *execute* the agent's publish script statement by statement,
which is not reachable through `dbt run` inside a grading zone. Business logic moved to
`pipelines/mart_rebuild.sql`; dbt keeps the staging layer, and the currency fix still runs
through it.

**The git half of check 1 is deferred, on the record.** The fixture world has no git history,
so `grade.py` checks the working-tree file. SEED_SPEC §3 freezes the commit Track A must
create. Recorded as `deferred` in the manifest rather than quietly dropped.

**The previous build's dimension was latently wrong.** A043 says the figure was "wrong in a
way no single table was wrong". Under an inner join a mixed read can only *understate* unless
the older dimension fans out — so the analyst's double-counting theory, which A043 requires to
be plausible, forces the older dim to have carried duplicates. I made those rows latent and
unobservable for a week (the accounts had no revenue until launch day), so **no reported
number was ever wrong from any single build**, which is the operative property. Recorded
rather than papered over.

**Two restatements of the torn tick are accepted.** A043 says the rows are "corrected in
place" without saying to what. "What the published build would have returned" and "what the
build that was landing would have returned" are both defensible and the world does not
disambiguate them. Grading one would be grading a coin flip, so `grade.py` takes either,
applied consistently across all four regions. Mixing them, deleting the tick, or recomputing
from the repaired mart all fail.

**On E1's self-criticism.** E1 suspected it had made its archetypes easier than the incidents
by giving every one a row-level provenance column. GT003 has none: no `build_id` on the
snapshot, no retained pre-delivery customer master, no loader audit row naming the deleted
duplicates. SEED_SPEC §0 names those three specifically as things that must not be added. The
one thing that does function as an index is `staging.stg_revenue_lines.loaded_at`, an ordinary
ingestion stamp present on every row, and the ablation shows it does not reproduce the figure.

## 5. Three defects the coordinator's GT001 audit caught in my work too

Checked deliberately rather than assumed.

- **F622 — oracle broken at the contract path.** My `solution.sh` had the same
  `duckdb.connect(db)` idiom. Fixed in all three of its Python blocks; the generator, grader,
  probe, fixture contract and baselines now all use `:memory:` + `ATTACH … AS wh` +
  `USE wh.warehouse`, and the suite stages every world at the contract filename so the
  collision cannot hide again. Verified: the oracle runs clean end to end at
  `var/warehouse/warehouse.duckdb`.
- **F620 — false-cause penalty defeated by a semicolon. I had it.** My D7 gave credit from the
  joined blob and took the penalty from list elements, exactly as GT001 did. The fix is two
  rules: credit and the unsupported-cause penalty read **the same unit** (one entry of
  `additional_causes`), and the causes we know are wrong here are named in the manifest and
  counted wherever they appear, which is unit-free by construction. `checklist_joined` is a
  permanent regression baseline and scores identically to `checklist`.
  I first tried splitting entries into sentences; it shredded the oracle's own two-sentence
  explanations into fragments and scored the correct answer −2. That approach is out.
- **F621 — substring test for a config key.** Not inherited. D3's static check uses anchored
  regexes and D6 is behavioural.
- **Grader crashing instead of scoring.** Every check now runs under a wrapper that converts
  an exception into zero for that check's whole denominator. `schema_vandal` is the permanent
  regression: it destroys three table schemas and scores 4.0 rather than raising.

Two further grader defects were found by the oracle itself, both score-invalidating:

- **D3 read a comment as live SQL.** The oracle's repaired script says in a comment which
  predicate it removed and why; the reject regex matched the comment and scored the correct
  answer zero for documenting itself. Comments are now stripped before matching.
- **D2's reference moved when it was earned.** It computed the escalated figure from
  `rev_snapshot` in the *final* world — but the correct repair restates that very tick, so the
  target evaporated the moment an agent deserved it, and a no-op agent was graded against the
  wrong number it had left in place. The reference is now the frozen manifest value.

## 7. The single biggest weakness in my own output

**D6 grades the pair of scripts the harness hands it, and I cannot prove that is the same
thing as grading the world.**

The probe executes `pipelines/mart_rebuild.sql` and `pipelines/bi_extract.sql` from the
agent's workspace. That is what makes it implementation-agnostic and what lets three genuinely
different fixes pass. But it means the check rests on a convention — that those two files are
what the scheduler runs — which is *documented in the runbook and nowhere enforced*. An agent
that hardens the mart by some route that leaves those two files unchanged, or that moves the
publish into a new file, fails a probe it has arguably satisfied; an agent that edits the
files without changing what the scheduler actually does passes one it has not. In the fixture
the scheduler is a JSON log with no executor behind it, so the convention is untestable here
by construction. Closing it needs Track A's scheduler to actually invoke those paths, at which
point the probe becomes a statement about the world instead of about two filenames. Until
then D6 is 3 of 20 resting on a convention, and I would attack it there first.

Two smaller ones, stated so they are not discovered later:

**The residual leak on the defining property.** After both fixes, an agent can still take the
08:15 tick, subtract the 08:30 tick, and brute-force live groupings for a set whose launch-day
revenue equals the difference. Nothing I can do about that short of making the arithmetic not
close, which would remove the agent's only way to *prove* the diagnosis. What that path yields
is *whose* money was counted twice — never that the dimension was a build behind — and D1's
token check requires naming the dimension or the previous build, so it scores 0 of 4 on the
primary cause. It shortens the search; it does not replace the evidence. I am reporting it
because it is the honest boundary of the claim in §2, not because I think it is fatal.

**D2 scans for a number.** One point for stating the escalated figure, graded by regexing
every number out of the artifact and matching within 0.2%. It is guarded against day-of-month
collisions (a bare integer never matches the millions reading), but it is still a
string-matching check standing in for "did you tell Finance what the number was". If the
figure had to move again I would rather add a field to the artifact contract than keep
widening the regex — and that is a §9.2.5 change, which is why I did not make it.
