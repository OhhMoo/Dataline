# The Jupyter plug — `jupyter.internal:8888`

The `notebook` slot's `jupyter` plug (`alkera_gateway.plugs`). The agent gets a real
jupyter-server on the episode network; every cell it runs writes one 9.2.2 row through
`alkera_gateway.native.audit.record`, the same writer the shims and fake services use
(gateway/NATIVE.md, "The one thing that must survive").

| file | what it is |
|---|---|
| `kernels/alkera-python/kernel.json` | the kernelspec, generated by `alkera_gateway.native.notebook.install_kernelspec(dir, interpreter="/usr/local/bin/python")`. `tests/test_notebook_plug.py` asserts it is byte-equal to the generator's output, so do not hand-edit it. Regenerate it with the generator. ds/da images install these same bytes as `python3` too (`install_audited_kernelspecs`, below). |
| `launch.py` | installs the kernelspec into `<sys.prefix>/share/jupyter`, then `exec`s jupyter-server with the flags that close every unaudited path (its docstring lists them) |

## What is audited, and how

`alkera_gateway/native/notebook.py` is an IPython extension that the kernelspec
preloads (`--IPKernelApp.extra_extensions=alkera_gateway.native.notebook`, plus
`reraise_ipython_extension_failures=True`, so a kernel that cannot load it does not
start). Each executed cell becomes one `jupyter.cell` row:
`op_class: exec`, `targets` = workspace files the cell created, changed or deleted (the
python shim's own snapshot diff, `shims/run.py`), plus any `ALKERA_SHIM_WATCH`
warehouse file it moved. The row also has the source's sha256 and an excerpt,
`execution_count`, `cell_id`, `kernel_id`, `notebook` (the path jupyter-server
gives the session) and `exit: error` with `ename`/`evalue` when the cell raised.
Silent executions, `user_expressions` and nested `run_cell` are covered too, and the
debugger is refused. The module docstring explains each case.

**`python3` is the audited kernel too, in the box.** `python3` is the name nbclient,
`jupyter execute` and a notebook with no kernelspec metadata start. ipykernel's wheel
ships its own `share/jupyter/kernels/python3`, which preloads nothing. So ds/da images
(`gateway/docker/Dockerfile`) and Harbor's ds/da variants
(`harbor/alkera_harbor/variant.py`) run
`install_audited_kernelspecs('/usr/local/share/jupyter', interpreter='/usr/local/bin/python')`.
That writes this kernelspec as `alkera-python` and over `python3`, with identical bytes.
The Dockerfile `cmp`s both against the checked-in file. `toolbelt_check.py` fails the
image if any spec in `jupyter kernelspec list --json` lacks the extension
(`kernelspecs.unaudited`). Measured with nbclient on a one-cell notebook:

| image | `kernel_name="python3"` | `kernel_name="alkera-python"` |
|---|---|---|
| `alkera-episode:head-da` (before) | 0 `jupyter.cell` rows | 1 row |
| `alkera-episode:t1-da` (after) | 1 row | 1 row |

The in-box guarantee covers only the installed data dirs. A kernel.json the agent writes
into `~/.local/share/jupyter/kernels/` is searched before `/usr/local/share/jupyter`.
A client in the box will start it, with or without the extension. The in-box kernel is
best-effort. The server plug below is the guarantee: it builds its one spec in memory
and reads no kernel.json.

**Two rows for a shimmed binary, by design.** `!duckdb ...`, `!dbt run` and `!python x.py`
inside a cell write the shim's row (with duckdb's table targets) AND the cell's row. A
call to a fake service from a cell writes both rows in the same way. The cell row's
`result.rows_during` gives the seq range written while it ran, so a reader can
group those rows under the cell.

The server-side flags, all set in `launch.py`:

- `kernel_spec_manager_class=…AuditedKernelSpecManager`: the server starts only
  `alkera-python`, and builds that spec in memory. Measured: `allowed_kernelspecs`
  alone still let `POST /api/kernels {"name":"python3"}` start ipykernel's built-in
  kernel, which has no extension and writes no rows.
- `terminals_enabled=False`: a terminal would be a second, un-redirected bash.
- token-less, xsrf off: reachable only on `episode_net` (`internal: true`, no
  published port).
- `root_dir=/workspace`: the contents API cannot reach the warehouse files bound
  under `/world`.

## Compose service (to be added to `compose.native.yml`, not added here)

```yaml
  # The notebook plug. Same image, same audit file, same workspace as the
  # episode container; jupyter-server serves the audited kernel only.
  jupyter:
    image: ${ALKERA_EPISODE_IMAGE:-alkera-stack:track-b}
    # ABSOLUTE interpreter: in this image a bare `python` would resolve to the shim
    # once the per-rollout overlay puts /opt/alkera/shims first on PATH.
    # Every row it wrote would land in the agent's action log.
    entrypoint: ["/usr/local/bin/python", "/opt/stack/jupyter/launch.py"]
    stop_grace_period: 2s
    networks:
      episode_net:
        aliases:
          - jupyter.internal
    environment:
      ALKERA_NATIVE_AUDIT: /audit/actions.jsonl
      ALKERA_SHIM_WORKSPACE: /workspace
      ALKERA_WORKSPACE: /workspace
      HOME: /root
      # Cell code is agent code: it needs the endpoint table the episode
      # container gets (JIRA_URL, PGHOST, AWS_ENDPOINT_URL, DBT_PROFILES_DIR, ...).
      # Lift episode.environment into an `x-native-endpoints: &native-endpoints`
      # anchor and merge it here with `<<: *native-endpoints`, so there is one table
      # and not two copies that drift.
    volumes:
      - "${ALKERA_EPISODE_WORLD:?episode world directory}/workspace:/workspace"
      - "${ALKERA_EPISODE_AUDIT:?episode audit directory}:/audit"
      - type: tmpfs
        target: /world/var/ledger
        read_only: true
        tmpfs:
          size: 4096
    healthcheck:
      # Read the port state, do not dial it, for the reason native-services
      # gives: no probe traffic may look like episode traffic. 8888 = 0x22B8.
      test: ["CMD", "/usr/local/bin/python", "-c",
             "import pathlib,sys;sys.exit(0 if any(f[1].endswith(':22B8') and f[3]=='0A' for f in (l.split() for l in pathlib.Path('/proc/net/tcp').read_text().splitlines()[1:])) else 1)"]
      interval: 2s
      timeout: 5s
      retries: 30
      start_period: 2s
```

The per-rollout overlay (`tasks/harness/container_episode.py`) must give `jupyter`
the same environment and binds it gives `episode`: `PATH` with the shims first,
`ALKERA_SHIM_BIN`, `ALKERA_SHIM_WATCH`, and the warehouse FILE binds. Without the
binds a cell cannot reach the warehouse. Without the watch, a cell that rewrites the
warehouse through the `duckdb` library writes a row that names no target, and the
row looks like no change was made.

## Verified, and not

Executed off-container: the 4-cell notebook through nbclient (one valid row per cell,
in order), double and mid-cell reload, `!cmd` / `%%bash`, silent execution,
`user_expressions`, debugger refusal, fail-closed kernel start
(`tests/test_notebook_plug.py`). `launch.py` was also run against a real
jupyter-server 2.21 on loopback. That check confirmed: `/api/kernelspecs` lists only
`alkera-python`, the default kernel is `alkera-python`, `/api/terminals` returns 404,
`POST /api/kernels {"name":"python3"}` is refused with `NoSuchKernel`, and a cell
sent over the kernel websocket wrote one row with `notebook: analysis.ipynb` and the
server's kernel id.

Not executed: anything in Docker. The image does not yet contain ipykernel,
jupyter-server, pandas or pyarrow: no `requirements*.lock` has the `notebook` /
`ds` extras. Containment P6 does not yet probe `jupyter.internal:8888`.
jupyter-server's connections are not in `destinations.jsonl`.
