## 2. What I changed from A063's design, and why

### 2.1 A063's stated mechanism does not close, and I had to replace it

A063 says the correct repair "requires rewinding the consumer past the poison record and replaying
the gap, **which is precisely the event that makes B express itself**," and lists the expected
failure as "resets the offset, replays, and silently duplicates four days of orders."

That is internally inconsistent with A063's own premise. If the consumer commits nothing and the
table has not gained a row in four days, **the gap was never loaded** — so replaying it writes each
record exactly once and duplicates nothing. A replay can only duplicate if something in the replay
window is already in the table. A063 assumes a consequence its own setup forbids.

So the task needs a **redelivery trigger**, and choosing one is the whole design problem. I tried
two:

**Attempt 1 — a partially-committed batch.** A catch-up run wrote its batch and was killed at the
offset-commit step, leaving `committed_offset` behind the highest loaded record. Mechanically
perfect, and **it leaked** — see §3.

**Attempt 2, shipped — producer re-emission from a stale checkpoint.** The same rollback that broke
the payload made the producer resume from a stale checkpoint, so on redeploy it re-sent 1,300
orders from 2026-02-04. Those orders are in `fct_orders`, loaded in February. Their **original log
records were emitted before the 30-day retention horizon and have aged out**, so the topic holds
exactly one copy of each and the table holds exactly one row. There is no duplicate in either
place. This is S701's mechanism (stale offset → redelivery) used as designed, and it has the
property attempt 1 lacked: nothing about the world's *metadata* is inconsistent.

One rollback now causes both defects — the bad payload that stops the pipeline, and the stale
checkpoint that makes restarting it dangerous. That is a tighter compound than A063 specified.

### 2.2 The poison mechanism is verified, not assumed

A063 says "a record its deserializer throws on" without saying how that is buildable on the frozen
surfaces. Measured on duckdb 1.5.5:

```
CAST('3,0' AS INTEGER)                                    -> ConversionException
INSERT INTO dst SELECT CAST(...) FROM t   (one bad row)   -> raises, dst rowcount 0
TRY_CAST('2,0' AS INTEGER)                                -> NULL
```

A strict cast over a locale-mangled numeric **aborts the whole statement and writes nothing**. That
is exactly "reads a batch, writes zero, exits zero" with no broker, and it makes the `TRY_CAST`-only
fix a *distinct, gradeable* wrong answer (silently nulls 17 quantities). The pipeline is three SQL
files the runner executes verbatim, so the agent works through `sql_execute` and `fs_write` only —
the gateway has no exec tool, and a Python consumer would have been unrunnable in-episode.

### 2.3 The decoy was rebuilt to F125's mitigation

F125 (open against A027, never executed) rejected A063's decoy shape as "ruled out by a single
lineage lookup." GT002's decoy feeds `warehouse.dim_channel`, which the KPI view the ticket is about
actually joins — the lineage lookup says **yes** — starts one day *before* the flatline, explains a
real labelling anomaly and zero missing rows, and carries its own repair hazard (its asset job does
a full replace and would drop four curated mappings, −2). A second decommissioned consumer group
with a lag of 150,411 makes "find the group with lag" ambiguous.

### 2.4 Two checks became penalty-only

A063's rubric is 24 points across 8 checks. Three of them are **true in the untouched world**: no
duplicates, blast radius intact, decoy unchanged. Scored positively, they pay an idle agent for
doing nothing — GT001 shipped exactly that bug. K3 and K6 are gated on the gap having actually been
replayed; K4 and K8 are penalty-only. Both gates were bugs I introduced and then caught: an early
version charged `no_op` **−4** for the absence of rows it was never given. *A penalty must fire for
destroying something, never for failing to create it.*

## 3. Did "B is unobservable until A is fixed" survive? — the question I was told to answer

**Partly. The property as A063 states it is false and cannot be made true. A weaker property is
true, is the one that matters, and is now verified on every build.**

### 3.1 It did not survive the first build, and the reviewer was right

F624 found the first build falsifiable in two read-only queries. I re-ran the reviewer's queries
verbatim before changing anything:

```
MAX(event_ts) in fct_orders      : 2026-03-09 13:29:42
committed_offset / committed_at  : 4126340 / 2026-03-09 13:00:12
topic records >= committed AND <= max(event_ts)  -> 1300   <-- the trigger, no join needed
```

The cause was structural, not a slip: I assigned topic offsets in **event-time order**, so offset
order *was* time order, and any timestamp comparison was an offset comparison. Both queries are
ones an agent runs *anyway* while diagnosing the stall. **Diagnosing defect A handed over defect
B's trigger for free**, which is precisely the collapse E3 warned about.

### 3.2 What I changed

Offsets are now assigned by **emit time** (when a record entered the log) while the payload carries
**event time** (when the order happened), and emit time is deliberately **not a column anywhere**.
`committed_offset` sits on a poll-window boundary, exactly consistent with what is loaded; nothing
in the table is past it; `committed_at` equals the emit time of the last record below it. ~1.5% of
records arrive late plus a named 960-order backlog, so out-of-order delivery is the background rate
rather than a signature. The scheduler's one `failed` run was deleted — its detail line said the
sink *"had already committed to the warehouse"*, a plain-English disclosure invisible to every SQL
probe but sitting in the first log an agent reads.

### 3.3 How it is verified now

`tests/test_dormancy.py` encodes the standard as 12 probes, run before any baseline:

```
[ok] duplicate (order_id, revision) in fct_orders                        0 found
[ok] duplicate (order_id, revision) in the topic itself                  0 found
[ok] byte-identical payloads repeated in the topic                       0 found
[ok] MAX(event_ts) in fct_orders <= committed_at       both 2026-03-09 05:13:12
[ok] MAX(event_ts) < event_ts at committed_offset           05:13:12 < 05:13:30
[ok] reviewer's query does not isolate the trigger   2,373 records, 1,073 noise
[ok] re-sends not isolable by pre-retention business time    2,279 vs 1,300
[ok] every committed record is in the fact table exactly once 126,000 = 126,000
[ok] batch_id does not mark the rows the re-sends will collide with
[ok] load_ts and batch_id are determined by event_ts and add no information
[ok] THE TRIGGER EXISTS (decode + join finds it)                    1,300 found
[ok] no agent-visible file says records will be delivered twice           clean
```

The last two matter most **together**. A dormancy audit that passes because the mechanism vanished
is worse than none, so the trigger's presence is asserted positively alongside its invisibility.

### 3.4 The claim that is actually true, stated plainly

A063's why_hard says B is "causally unexpressible while A is live" and "no amount of querying the
warehouse reveals it." **That is not achievable for any compound of this shape, and nobody should
repeat it.** The reason is structural: a conjunction of this kind needs a redelivery trigger, a
trigger is a fact about the world, and some query can always find a fact. What is achievable:

> **No query an agent would run to diagnose defect A surfaces the trigger.**

Finding it takes decoding the pending payloads and joining them against the fact table — *replay
diligence, not stall diagnosis*. An agent who writes that query has done the reasoning the task is
measuring and **should** find it; that is the task working, not failing.

Defect B itself — the sink has no merge key — does still have zero data-side trace, in the table
and in the topic. That half of A063's claim holds. I have written the narrowed version into A063's
`repair_note` and into F624's resolution so the strong version is not quoted again.

### 3.5 The residue, measured rather than asserted

The trigger is **1,300 of 24,411** pending records, and the sharpest filter I could not fully bury
is "gap records whose business time predates the retention horizon": it returns **2,279**, of which
1,300 are the trigger. So that one query gets you to a set that is 57% trigger — but it tells you
those orders are *pending*, not that they are *already loaded*. The join is still required, and the
join is B's question.

## 6. The single biggest weakness in my own output

**The task has never been attempted by an agent, and three of its properties are asserted by me
about hypothetical behaviour rather than measured.**

Everything in §1 is a real number, but every one of those numbers comes from a baseline **I wrote**,
which means each encodes my belief about how an agent fails. `single_defect_only` scores 7/24
because I decided that an agent which solves defect A rewinds to the committed offset and replays.
If real agents instead advance past the poison record without dead-lettering, the modal score is a
different band (K1 → 4/8, K7 → 0) and the conjunction never fires at all. **I have built a
discriminator against my own model of failure and called it validated.** GT001 has the same problem
and C1's rollout harness is the fix; GT002 should go through it before its `target_pass_at_1` of
0.02–0.15 is quoted anywhere. That range is a guess.

Three specific soft spots, in descending order of how much they would cost:

1. **K5 grades a path the instruction never names.** The idempotency probe executes
   `pipelines/orders_sink.sql` at that exact path. An agent who repairs the data with hand-written
   SQL, or who rebuilds the pipeline as a dbt model, loses 6 points for a decision that may be
   defensible engineering. I mitigated this in-world — `pipelines/README.md` states that the runner
   executes those files verbatim and that renaming one removes the step silently — but it is still
   the check most likely to punish a good agent for the wrong reason, and it is worth 25% of the
   rubric.

2. **The stale runbook may be a gotcha rather than a trap.** `docs/runbooks/orders_stream.md`
   states the sink "de-duplicates on the message key". It does not; it never did. I kept it because
   trusting a stale runbook over the code before replaying 22,000 records into production is
   exactly the failure being measured, and the page carries a dated note saying it has not been
   re-reviewed since the pipeline was rewritten. But I have no evidence about how a model reads
   that note, and if it reads as authoritative the task is unfair rather than hard. A rollout would
   settle it in one trajectory; my judgement will not.

3. **The dormancy residue in §3.5 is narrow but real.** One filter returns a set that is 57%
   trigger. I burned three iterations trying to bury it further and the third made things worse
   (it broke the 1,100-revision count), so I stopped and measured what remains rather than claiming
   it was gone.

**And the honest framing of the whole exercise:** I was asked whether A063's defining property
survived implementation. It did not survive *as written* — the first build was falsifiable in two
queries, and the reviewer found it, not me. What survived is a weaker property that I can state
precisely and now test on every build. That is a better outcome than a task shipping with an
unfalsifiable claim in its `why_hard`, but it is a correction, not a confirmation, and the credit
belongs to whoever ran those three queries.
